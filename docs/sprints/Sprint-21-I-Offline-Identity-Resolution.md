# Sprint 21-I — Isolated identity verification and principal resolution

Baseline: `18dba22cb2ac4e09058de3158054e8c3c94e9360`, branch `codex/sprint-21-b-contracts`.

`identity_resolution.py` adds an unregistered offline resolver with injected scripted principal reader and credential verifier. No environment, actual credentials/hashes, HTTP dependency, routes, sessions, database, deployment or proxy configuration are read or composed. It is a fixture contract and policy checkpoint, not application authentication.

The parser requires one Authorization field value in an explicit tuple. It rejects duplicates (including equal duplicates), non-Basic schemes, malformed framing, whitespace in tokens, noncanonical base64, invalid UTF-8, empty credential fields, control characters and oversized input. The synthetic policy accepts case-insensitive Basic scheme spelling and exact UTF-8 credential bytes without normalization. Passwords containing colons remain intact after the first separator. This deliberately strict policy must be reviewed for compatibility before real HTTP wiring.

The trusted principal reader returns a strict enabled principal record: exact username, stable principal ID, credential version/format, permission epoch and finite explicit scope grants. Unknown, disabled, mismatched or malformed records deny. Requested scope must equal an allowed organization/collection/module/topic tuple, never a cross-product of module/topic lists. Reader/verifier execution sources must be `unit_test`; callbacks must be synchronous, and the verifier must explicitly support the record's format. Missing/unsupported capabilities deny rather than falling back.

The injected verifier sees an immutable credential attempt and a deep-copied principal record; it must return exactly boolean True. Truthy objects, integers, metadata or release flags cannot certify identity. One verification attempt is permitted per resolver session; failures and attempted reuse are terminal. There is no retry, fallback or concurrent dispatch. The principal is reread after verification and compared exactly to prevent rotation/revocation during verification. Reader/verifier identities and supported-format policy are bound to the issued handle.

Success issues an immutable canonical context with request ID, requested scope, server principal/policy/grants and a SHA-256 digest, excluding password and raw Authorization header. Handle ownership is local to its issuing session; clones, cross-session handles and modified contexts deny. Recheck validates current enabled state, principal/credential/permission versions, grants and capability policy. A denied session cannot regain authority after state restoration. Sensitive attempt/context fields are hidden in normal representations; bounded failure reasons exclude callback exception messages.

A finite monotonic request deadline covers initial reads, verifier work, final reread and subsequent rechecks. Backward/invalid clocks deny. Synchronous callbacks cannot be forcibly interrupted; deadline enforcement is observational before and after work. A single-attempt session is not fleet-wide credential rate limiting, constant-time whole-request behavior, secure password hashing, real credential isolation, or a publication barrier. The verifier's internals remain trusted injected fixture behavior, not sandboxed code.

Every result retains `authenticated_scope_verified=false`, `semantic_grounding_verified=false`, `release_authorized=false`, `production_enabled=false` and `proposition_to_inference=closed`. It is not wired to 21-H answering or a public authentication route. A future real hash verifier, generic external authentication errors, request rate control, application dependency wiring, gateway forwarding validation, credential configuration and CSRF review remain separate reviewed work. Existing admin credentials were not inspected or copied.

Focused tests cover successful synthetic resolution/recheck, malformed/duplicate/header-only credentials, verifier failure/truthy metadata, supported format policy, foreign/cross-product scope denial, disabled/missing principals, credential/permission rotation and revocation, reader/verifier swaps, forged handles, single-use attempts, full-session expiry, final-read expiry and invalid clocks. No migration, database mutation, embedding/vector/provider call, benchmark, frozen record/ADR-037 change or PR #1 merge is included.

Next: draft additive catalog schema and the migration application gate outside automatic migration discovery, then a dry-run backfill planner using supplied synthetic records/byte fixtures. Actual database work requires a separately reviewed target/schema/backfill plan; current backend startup automatically applies Alembic head. Production answering remains blocked on real identity/storage/retrieval/provider/publication integration, empirical/final acceptance and explicit release authorization.

Validated 2026-10-13: 636 relevant offline tests passed, including 74 new identity tests and 562 existing regressions. Packet, review, presentation and readiness evidence integrity were valid with no errors; readiness remained blocked and production disabled. Final-read capability replacement is checked before issuing or rechecking a principal handle.
