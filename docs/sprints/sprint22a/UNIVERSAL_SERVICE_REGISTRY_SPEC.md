# Universal service registry

Services belong to an exact `(tenant_id, application_id, service_id)` scope. A service ID is stable within that scope; the same local name in another application never grants access. Identifiers are bounded and validated rather than interpreted as paths, SQL or URLs.

The canonical service record carries schema version, service identity, name, type, environment, monitoring status, explicit health policy, creation timestamp and update timestamp. Dependencies are normalized separately and derived through scoped graph queries rather than maintained as an inconsistent second list inside service records. UTC timestamps and canonical serialization permit deterministic snapshots.

Exact version-1 keys are `schema_version`, `tenant_id`, `application_id`, `service_id`, `service_name`, `service_type`, `environment`, `monitoring_enabled`, `health_policy`, `registered_at`, `updated_at` and `configuration_ref`. Unknown keys are rejected. `configuration_ref` is a SHA-256 evidence/configuration reference. Types are `API`, `WORKER`, `DATABASE`, `FRONTEND`, `QUEUE`, `AUTH` or `OTHER`; environments are `local`, `development`, `staging` or `production`. Enabled monitoring is rejected outside local/development. Timestamps normalize to UTC microseconds, and updates cannot predate registration.

Identity syntax is ASCII letters/digits followed by letters/digits, dot, underscore or hyphen, with a maximum of 128 characters. Reserved universal names and recognizable credential prefixes are rejected. Service names use the same bounded character set with spaces permitted. Canonical records have an 8,192-character serialization budget. Health policies have exactly `required_checks` and `max_age_seconds`, at most 32 distinct checks and a 1–86,400-second explicit freshness limit.

The development seed represents `sentinel-ai` / `sentinel-api`. Its approved check is `process-liveness`; freshness is an explicit development policy. That policy describes a callable liveness signal, not HTTP availability, database readiness, semantic correctness or production reliability. Registering a service performs no collection and no external connection. Other application names are future registration targets, not integrated production services.

## Authorization

Every operation requires an explicit issued authorization context. Existing `GovernedAuthenticationSession` authentication and current-principal rechecks are reused. A server-configured grant maps an exact authenticated document `EvidenceScope` to an exact SRE tenant/application and allowed actions. Organizational scopes do not automatically confer universal SRE access.

Read, configure, ingest, validate and incident capabilities are distinct. A caller cannot authorize itself by placing a tenant ID, application ID or validation label in a record. Authentication sessions remain bound to their actual issuing catalog; caller-created principal-shaped objects cannot replace issuance. Shared supervisory access requires separately configured exact grants; no global wildcard is inferred from Sentinel's name.

## Durability and evolution

`SREStore` uses an explicitly created or opened private local SQLite database, an existing repository technology. Numbered SQL migrations, schema integrity checks, foreign keys and synchronous durable transactions protect restart behavior. This store is separate from live PostgreSQL catalogs and is never silently installed at application startup. Migration support does not claim that production PostgreSQL integration has been completed.

Registration and configuration audit entries share their write transaction. Repeating the same canonical registration is idempotent and returns `DUPLICATE` without another audit entry; changed registration bytes under the same identity cause `REGISTRATION_CONFLICT`. Updates require authorized configuration access, an expected revision and a nondecreasing update time. Only service name, monitoring status, health policy and configuration reference are mutable through this interface. Credentials, session tokens and raw authentication material are excluded from registry records.

Explicit lifecycle APIs are `SREStore.create`, `SREStore.open`, `SREStore.upgrade` and `close`. Storage schema version is 2, independent of version-1 records. Creation can construct version 1 for compatibility exercises; opening an old store does not silently migrate it. Explicit upgrade applies numbered migrations transactionally after integrity checks. The private absolute database path and its parent must be owned by the current user and inaccessible to group/other users. Creation refuses an existing path.

Default per-tenant/application capacities are 256 services, 10,000 observations, 50,000 audit entries, 1,024 dependencies and 1,000 incidents. Trusted composition may supply bounded positive `Limits`; these are local resource limits rather than production thresholds. Capacity exhaustion rejects the entire new write transaction with `RETENTION_CAPACITY_REACHED`. No evidence is silently purged. Review, export or approved retention evolution is required before increasing a full store's capacity. Observation queries default to the newest 100 records, permit an explicit maximum of 10,000 and return the selected records in ascending source-time/ID order. Other scoped lists are bounded by their corresponding storage capacities. Integrity verification traverses scoped records and audit history, so these limits also bound verification work.

The explicit `backend/scripts/sre_local_rehearsal.py` creates the first Sentinel development registry in a new private output directory. It uses a fresh ephemeral local process identity, not Rain's installed operator credentials. The recorded rehearsal starts with `UNKNOWN`, explicitly collects one current callable-liveness observation and records the same evaluation after reopening the store. Its `HEALTHY` result applies at that evaluation time and under the 60-second development liveness policy; it is not a continuing claim about the running daemon.
