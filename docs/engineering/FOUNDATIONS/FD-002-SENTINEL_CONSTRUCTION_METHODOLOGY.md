# FD-002 — Sentinel Construction Methodology

This foundation records the construction method already established by the
[constitutional subsystem pattern](../../architecture/SENTINEL_SUBSYSTEM_PATTERN.md),
[cognitive doctrine](../../architecture/cognitive/COGNITIVE_ARCHITECTURE_DOCTRINE.md),
and [coding standards](../CODING_STANDARDS.md). It does not supersede an ADR.

## Begin with responsibility

Read the governing philosophy, accepted decisions, sprint contracts, and current
implementation before changing a capability. State the operator's mission, the
capability's responsibility, and the authority it must not acquire.

Bridge observes. Intelligence discovers patterns. Governance protects integrity.
Systems observes and maintains platform availability. The interface communicates;
backend specialists compute. A menu item is complete only when its workflow is
connected to authoritative data and handles empty, unavailable, and rejected states.

## Build in the established order

Define language and authority boundaries, then explicit models. Builders organize
structure. Validators independently check integrity. Renderers communicate the
validated result. Engines and application services coordinate specialists without
performing their judgments. HTTP routes own transport and dependency composition.

Reuse established faculties instead of introducing a competing reasoning pipeline.
A formatter may explain a result but may not modify its judgment. Storage records
outcomes but may not determine their validity.

## Preserve evidence and history

Use stable, source-scoped identifiers. Resolve exact references before abbreviated
ones. Retain missing and ambiguous references as limitations. Never manufacture
provenance, semantic truth, or causal relationships from document mentions.

Record actual acquisitions separately from inferred understanding. Preserve
organization boundaries and immutable cognitive history. Rejected, conflicted,
and insufficient outcomes remain historical evidence.

## Verify the complete workflow

Test the failure boundaries that could create false success: unsupported evidence,
unresolved identities, unavailable dependencies, rejected credentials, incomplete
schema, and failed persistence. Then verify the browser/API/storage/response path
against the local running installation. Passing synthetic tests does not establish
an independent assessor's empirical accuracy.

Report measured readiness separately from model configuration, evidence confidence,
constitutional admissibility, and research acceptance. Never substitute an always-
healthy status or perfect score for an actual assessment.

## Deliver coherently

Keep implementation, validation, and deployment in the operator's local checkout.
Preserve private environment settings and persistent storage. Commit completed
changes with their documentation and push the working branch to GitHub when the
operator authorizes it. Leave unfulfilled acceptance gates visible.

Sentinel recommends. Humans authorize. No observation, plan, reflection, or
verification result grants execution authority.
